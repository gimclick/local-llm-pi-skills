# Triage

Move issues on the project issue tracker through a small state machine of triage roles.

If this repo treats external pull requests as a request surface (see the issue-tracker config), triage covers them too: **a PR is an issue with attached code**, using the same roles, same states, and same machine, with a few deltas marked "for a PR" below. Resolve a bare `#42` to an issue or PR per the tracker config.

Every comment or issue posted to the issue tracker during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Scope and boundaries

`triage` is the on-ramp for work that arrives from outside: raw bug reports, incoming feature requests, or an external PR. It is not a step in the spec flow. Tickets that `to-tickets` published are already agent-ready, and running triage over them re-does work that was already done.

The write surface is narrow and fixed: labels, comments, closure, and files under `.out-of-scope/`. Triage never creates an issue, never edits an issue body, never adds or removes a sub-issue or a blocking edge, and never assigns an issue. It cannot advance a dependency chain; closing a blocker is the maintainer's, and a blocker close is never part of a `ready-for-agent` write set.

## Roles

Two **category** roles:

- `bug`: something is broken
- `enhancement`: new feature or improvement

Five **state** roles:

- `needs-triage`: maintainer needs to evaluate
- `needs-info`: waiting on reporter for more information
- `ready-for-agent`: fully specified, ready for an AFK agent
- `ready-for-human`: needs human implementation
- `wontfix`: will not be actioned

For a PR, the same states read against the attached code: `ready-for-agent` means a brief is attached and an agent should take the next step on the diff; `ready-for-human` means it's ready for a human to merge.

Every triaged issue should carry exactly one category role and one state role. If state roles conflict, flag it and ask the maintainer before doing anything else.

These are canonical role names. The actual label strings used in the issue tracker may differ. The mapping should have been provided to you. If not, tell the user to run `/skill:setup-matt-pocock-skills`: it is user-invoked, so name the command and do not attempt it.

State transitions: an unlabeled issue normally goes to `needs-triage` first; from there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time; flag transitions that look unusual and ask before proceeding.

## Tracker and label configuration

Resolve both before touching anything:

- **Operations**: `docs/agents/issue-tracker.md`, the file `/skill:setup-matt-pocock-skills` writes. It names the tracker, the target repository, the read and write commands, and any capability marked **unverified**. On GitHub pass the target explicitly with `-R` rather than re-inferring it from the remotes.
- **Role mapping**: `docs/agents/triage-labels.md`, which maps the canonical roles to the label strings this tracker actually uses.

If either file is missing or its section is unconfigured, name the command the human should type (`/skill:setup-matt-pocock-skills`) and stop. It is user-invoked, so name it and never attempt it.

Before any label write:

- Read the mapping for the role you mean, and use the mapped string rather than the canonical name.
- Read the labels that exist (`gh label list -R <owner>/<repo> --json name --jq '[.[].name]'`, or the tracker doc's equivalent) and check the mapped label is one of them.
- A label that does not exist is a fact to report, never a label to create, rename, or substitute. Name the missing role, and leave the issue's labels untouched.
- Keep the upstream rule: exactly one category role and exactly one state role per item. Removing the state role being replaced is part of the write set, not a separate action.

## Readiness guard for `ready-for-agent`

This guard is separate from the classification above. It adds no role, no state, and no label: `ready-for-agent` keeps its upstream meaning, and an issue that waits on another issue is not reclassified.

Before recommending or applying `ready-for-agent`, read the issue's open blocking relationships using only the read capability documented in `docs/agents/issue-tracker.md`:

- On GitHub, use the native gate that file defines: `gh api repos/<owner>/<repo>/issues/<n> --jq .issue_dependencies_summary.blocked_by`, an open-only count where `0` means startable. `blockedBy.totalCount` counts every edge, closed blockers included, and is never the live gate. Where the tracker doc marks the capability **unverified**, use its documented fallbacks (`gh issue view <n> -R <owner>/<repo> --json blockedBy` with `[.blockedBy.nodes[] | select(.state == "OPEN")] | length`, guarding that the node array is not truncated, or a `Blocked by: #<n>` body line) and name which gate you read.
- On any other tracker, use only the read operation that file documents. If it documents none, say so.

Then, by what the gate returned:

- **Open blockers verified (count above zero):** report them by number and state that the issue is not startable. `ready-for-agent` is **not** applied, and no approval lifts this: the role means an agent can take the issue now, and an issue with an open blocker does not mean that. Approval may authorize continuing the investigation, running the grilling step, or posting a brief as a comment without the role. It may also authorize resolving a blocker as a separate tracker operation with its own explicit approval, which is not a label write and is never bundled with the role. After that operation, re-read the gate; the role may be applied only once it returns zero.
- **Zero open blockers verified:** the role may be recommended and applied, subject to the write-set approval below.
- **Readiness unverified** (capability unavailable, marked unverified, or the gate could not be read): report readiness as **unverified**, name the gate that could not be read, and do not apply `ready-for-agent` automatically. The maintainer may apply it as an explicit instruction with that caveat stated. Absence of evidence is not an unblocked issue.
- Stop for human direction in every case. Remove no blocker, add or reorder no blocking edge, close no dependency, and invent no state for work that is specified but waiting. Keep closed edges in place; they record what was resolved.

No new state, role, or label covers a waiting issue. Whatever role the issue already carries stays in place while its blockers are open.

## Invocation

The maintainer invokes `/skill:triage` in Pi (upstream harnesses type `/triage`) and describes what they want in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the issue tracker and present three buckets, oldest first:

1. **Unlabeled**: never triaged.
2. **`needs-triage`**: evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes**: needs re-evaluation.

When PRs are in scope, include external PRs in these buckets and tag each line `[PR]` or `[issue]`. Discovery surfaces only *external* PRs (the tracker config defines who counts as external), so a collaborator's in-flight PR is not triage work. This filter is discovery-only; an explicitly named PR is always triaged regardless of author.

Show counts and a one-line summary per item. Let the maintainer pick.

## Triage a specific issue or PR

1. **Gather context.** Read the full issue or PR (body, comments, labels, author, dates; for a PR, the diff too). Parse any prior triage notes so you don't re-ask resolved questions. Explore the codebase using the project's domain glossary, respecting ADRs in the area. Run two checks against the codebase: (a) **redundancy**: search for an existing implementation of the requested behavior by domain concept (not just the request's wording), and report where you looked. If found, it's an already-implemented `wontfix` (step 5). (b) **prior rejection**: read `.out-of-scope/*.md` and surface any that resembles this request.

2. **Recommend.** Tell the maintainer your category and state recommendation with reasoning, plus a brief codebase summary relevant to the request (including whether it's already implemented). Wait for direction.

3. **Verify the claim.** Before any grilling, check that the claim holds up. For a bug, reproduce it from the reporter's steps. For a PR, confirm the diff does what it claims: check it out, run the relevant tests or commands. Report what happened: confirmed (with code path), failed, or insufficient detail (a strong `needs-info` signal). A confirmed verification makes a much stronger agent brief.

4. **Grill (if needed).** If the request needs fleshing out, run `grilling` and `domain-modeling`, and grill it into shape a round of questions at a time, sharpening domain terms and updating `GLOSSARY.md`/ADRs inline as decisions land. Pi has no Skill tool: both are model-invoked here, so check each name is in the agent's `<available_skills>` block at the point of use and read its `SKILL.md` in this checkout to follow it. A name that is not loaded is a missing dependency: report it and keep the rest of triage going with what you already have, rather than improvising the missing methodology. Run one at a time, never in parallel, and never delegate.

5. **Apply the outcome.** State the exact write set first and wait for the maintainer's approval: the labels to add and the label to remove, the comment to post and whether it closes the issue, and any file to write under `.out-of-scope/`. Apply nothing until approved. Then:

   - `ready-for-agent`: apply the role only where the readiness guard above verified zero open blockers, and post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)). Where blockers are open or readiness is unverified, post the brief without the role and report what the gate returned.
   - `ready-for-human`: same structure as an agent brief, but note why it can't be delegated (judgment calls, external access, design decisions, manual testing).
   - `needs-info`: post triage notes (template below).
   - For `wontfix`, close the issue, with the comment depending on *why*:
     - **Already implemented**: the change already exists in the codebase. Point to where it lives; do **not** write to `.out-of-scope/` (that KB is for *rejected* requests, not built ones).
     - **Rejected (bug)**: give a polite explanation, then close.
     - **Rejected (enhancement)**: write to `.out-of-scope/`, link to it from a comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: apply the role. Optional comment if there's partial progress.

## Quick state override

If the maintainer says "move #42 to ready-for-agent", trust them for everything except the readiness guard: read the gate before the role is applied. State the write set (role changes, comment, close) before acting. If the gate verifies open blockers, do not apply the role; report the blockers and offer the approved alternatives (continue the investigation, post a brief without the role, or resolve a blocker as a separate authorized operation). If readiness is unverified, say so and apply the role only on that explicit instruction with the caveat stated. Skip grilling. If moving to `ready-for-agent` without a grilling session, ask whether they want to write an agent brief.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

## Resuming a previous session

If prior triage notes exist on the issue or PR, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.

## Execution constraints

This fork runs one inference slot at a time, and triage is one foreground session:

- **No delegation.** Triage launches no subagent, and the grilling step above runs in this session.
- **No parallel or background work.** At most one model request live.
- **A bulk pass is a listing, not evidence.** The "show what needs attention" pass is a cheap selection aid that returns bodies, not comments. Work one issue at a time, and when asked to cover many, read each issue's comments and prior triage notes before recommending, so an issue already carrying a resolution note does not get a fresh brief.
- **No scheduler.** Triage picks no next ticket, dispatches no frontier, and starts no implementation. `implement` stays the human's, and closing a ticket stays the human's.
