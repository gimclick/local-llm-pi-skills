`to-tickets` is now registered in this fork's `pi.skills` manifest, as the eighth skill. It stays user-invoked: `disable-model-invocation: true` keeps it out of the agent's `<available_skills>` block, so only the human can fire it, by typing `/skill:to-tickets` with an optional repository-relative spec path or issue reference after it. Its `agents/openai.yaml` policy is unchanged.

Upstream's methodology is preserved as it stood: codebase exploration and prefactoring, small independently verifiable vertical slices, blocking-edge dependency analysis, the expand/migrate/contract sequence for wide refactors, the human quiz and approval before anything is published, blockers-first publication, and the local markdown tracker's one-file-per-ticket layout. The ticket templates are upstream's, plus one source-traceability line each.

What this fork adds is source discipline, not new behaviour. When handed a committed spec file, the skill reads that file from the repository, names the ref it searched and the commit that holds the authoritative version on that ref, and reports whether the working copy differs from it. The ref is the branch the build will run from, stated in the open: a commit from a stale or unrelated branch is never picked silently. It does not build tickets from uncommitted edits or from conversation memory, and where the source is ambiguous or uncommitted it stops and asks which source is authoritative before publishing. The spec's contracts travel into the tickets unchanged: acceptance-fixture identifiers, commands as invoked, messages byte for byte, exit codes. The skill does not invent a requirement or rewrite the canonical spec.

Each ticket cites what it was cut from, as a repository-relative spec path plus a commit-pinned permalink, and names the acceptance criteria and fixture identifiers it owns. Every required fixture gets one primary owner, or is recorded as already passing at the commit the work starts from; a later ticket may reference an earlier fixture as regression coverage, which is not a second implementation deliverable. Behaviour already implemented gets no ticket.

Parentage follows the source. A spec committed as a Markdown file yields standalone implementation issues: no issue is opened to duplicate the spec, and implementation tickets are never attached to a `wayfinder:map` issue, whose children stay decision tickets. A separate implementation umbrella issue is allowed only on the user's explicit approval, and is never created automatically. An existing source issue keeps upstream's sub-issue behaviour. The GitHub tracker template now records these rules where it had left the file-backed case an open question.

Labels are conditional, so they cannot fail a publication: `ready-for-agent` is applied only when the configured triage-label document maps that role and the label already exists on the tracker. Otherwise the skill reports the unavailable label and publishes without it, and never creates a label. Nothing is delegated, and independent tickets do not imply parallel execution: the skill publishes an artifact, and the work is one focused fresh session at a time in dependency order. `implement` and `implement-spec` stay out of this fork's manifest.

`README.md` records eight registered skills and adds `to-tickets` to the Pi table. The to-tickets docs page carries the Pi banner, the source and parentage rules, and the distinction between registered and runtime-tested: `to-tickets` is registered and has never run in this fork. The stale `prototype` status in the README and the wayfinder page is corrected narrowly: standalone logic generation and a map's `prototype` ticket artifact have both been produced, while the verdict that resolves a prototype ticket, the UI-variants branch, and practical usefulness have not.
