`code-review` is now registered in this fork's `pi.skills` manifest, as the tenth skill. It stays model-invoked: its frontmatter carries no `disable-model-invocation`, so Pi advertises it by name, description and path in the agent's `<available_skills>` block and loads it by reading its `SKILL.md`, and the human can force it with `/skill:code-review`. Its `agents/openai.yaml` is unchanged and carries no `policy` block, the same shape as the other model-invoked skills in this fork. The Claude plugin manifest is untouched: the promoted set stays 27.

The two-axis methodology is upstream's and is preserved unchanged. **Standards** and **Spec** stay separate axes with no blended verdict: Standards reports documented-standard breaches (which can be hard) and baseline smells (always judgement calls), a documented repo standard overriding the baseline; Spec reports requirements missing or partial, behaviour that was not asked for (scope creep), and requirements that look implemented but where the implementation looks wrong. The twelve-smell Fowler baseline from _Refactoring_ ch.3 is pasted in full and unchanged, since the reviewer has no other access to it. Citation requirements are unchanged: a standards finding names the file and the rule, a smell names itself and quotes the hunk, a spec finding quotes the spec line. The per-reviewer limit stays under 400 words, the final report stays two sections under `## Standards` and `## Spec`, and the closing summary still names a worst issue within each axis and declines to pick a winner across axes, because that is the reranking the separation exists to prevent. The name clash, the no-spec-available path, and the "no overall winner" rule are upstream's.

What is adapted is execution. Upstream issues both sub-agent calls together; this fork runs one inference slot, so the two reviews run sequentially, one fresh context each. The parent launches the Standards reviewer in the foreground and waits for it to return, then launches the Spec reviewer as a separate call, and never has two model requests live at once. Neither reviewer receives the other axis's brief, question, or findings. The frontmatter description now says "two separate fresh-context reviewers, one at a time" instead of "parallel sub-agents", which is the only metadata change; the skill stays model-invoked either way.

The evidence is the parent's, because the reviewer is read-only. Pi's packaged `reviewer` agent carries read, grep, find and ls and no shell, so it cannot run `git diff` or resolve a ref itself. The parent therefore collects the full diff text of the pinned range, the commit list, and the axis-specific evidence (the standards-source files for Standards, the spec path and full text for Spec), and hands it over in the brief. Completeness is checked before delegation: the text sent is compared against `git diff --stat` for the range, and the axis evidence is checked the same way, every standards file pasted in full and the spec taken as the version held at the reviewed HEAD SHA. One axis stays one reviewer with one context, so a diff that will not fit one brief is not split across two calls for the same axis: that would be a second reviewer, and stitching two partial passes together presents them as one review of the range. The range is narrowed by asking for a tighter fixed point, or the partial pass is labelled **partial coverage** and names the files and hunks left out. Nothing is truncated, no summary stands in for code, and a partial review is never presented as covering the whole range. The packaged `reviewer` agent's own default output (a P0/P1/P2 severity ladder and a `Merge verdict: BLOCK, OK, or OK with notes` line) is named in both briefs and overridden: each reviewer answers in the skill's own categories with a citation on every finding, returns no severity ladder, no merge verdict and no ranking across the axes, and the parent owns the report shape. The packaged agent and its system prompt are untouched. Where surrounding context is needed, the brief names the files the reviewer may read, which is evidence about the change and not a licence to review outside the range.

Diff authority is now pinned to commits rather than to moving names, keeping upstream's three-dot merge-base semantics. The fixed point must be supplied by the user and is never guessed. The skill records the reference supplied, the merge-base SHA, and the reviewed HEAD SHA, and runs the diff and the commit list on those SHAs, so a branch moving during a review cannot change what was inspected. It fails closed before any reviewer is launched on a bad reference, an unresolvable comparison, or an empty diff. It names staged, unstaged and untracked changes as outside the committed review range, and a positional reference that reaches unrelated history is reported and tightened by asking rather than reviewed silently. The same SHAs are repeated in the final report, so findings stay verifiable after HEAD moves.

Corrections stay diagnostic. The skill implements no fixes, writes no files, commits nothing, pushes nothing, and writes nothing to an issue tracker. A later correction pass is a **delta review**: the previous reviewed HEAD SHA becomes the new fixed point, the range is named as a delta, and findings outside it are not reapproved. It is not a comprehensive reapproval of the final codebase, and the skill is not run in a loop until the report comes back clean.

One upstream workaround is deliberately not copied. The known runaway-spawn bug is answered upstream by appending a guard line to both briefs; Pi's harness already keeps a child from fanning out on its own, so that guard is not added here. The upstream setup pointer is now Pi syntax: the skill names `/skill:setup-matt-pocock-skills` and does not attempt to invoke that user-invoked skill on the user's behalf.

The fallback is labelled, not hidden. Where no suitable reviewer agent is configured (checked with `subagent({ action: "list" })` rather than assumed), the skill runs both axes in this session, one after the other, and labels the report a **foreground-only review**: it states that the two axes did not get independent contexts and that reasoning already in the session may have shaped what the review found. A foreground-only review is never presented as an independent one, and citations, both sections, and the no-blended-verdict rule still bind. The report also states which mode ran, and now states the coverage: whether each axis reviewed the whole range or only part of it, naming what is missing where it is partial.

`README.md` records ten registered skills, adds `code-review` to the Pi table as model-invoked, and marks it registered but not runtime-tested: no review has been exercised in this fork, so it joins the untested list. The `tdd` entry's stale claim that `code-review` is unregistered is corrected in the same sentence. The engineering bucket README and the top-level promoted listing now describe the reviewers as separate fresh contexts, sequential in this fork and parallel upstream, so the parallel wording stops being misleading. The code-review docs page carries the Pi banner, the Pi invocation, the pinned-range and delta-review behaviour, and the correction to upstream's guard-line workaround. `AGENTS.md` moves the `pi.skills` count from nine to ten; no other policy in it changed. `implement`, `tdd`, and every other skill implementation are untouched.
