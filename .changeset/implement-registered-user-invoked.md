`implement` is now registered in this fork's `pi.skills` manifest, as the eleventh skill. It stays user-invoked, unchanged in its metadata: its frontmatter already carried `disable-model-invocation: true` and its `agents/openai.yaml` already carried `policy.allow_implicit_invocation: false`, so it is absent from the agent's `<available_skills>` block and only the human can fire it, by typing `/skill:implement` with an optional issue reference or repository-relative spec path after it. The Claude plugin manifest is untouched: the promoted set stays 27.

The upstream lifecycle is preserved: consume the work described by the user, a spec or a ticket; fetch an explicitly referenced issue and state its title before implementing; drive `tdd` at approved seams; run typechecking and focused test files regularly and the full available suite once near the end; review the implementation; commit to the human-selected branch. One invocation is still one ticket in one fresh session, and the skill is still not a scheduler: it picks no next ticket, dispatches no frontier, and runs no two sessions side by side, so `implement-spec` stays out of the manifest.

Authority over the input is now explicit. An issue reference is resolved through `docs/agents/issue-tracker.md`, and on GitHub against the tracker doc's **Target repository** line with `-R` passed rather than re-inferred from the remotes, so a fork with two GitHub remotes cannot write into the wrong one. The issue is the scoped task and the specification is authoritative for behaviour: the skill reads the spec at the exact commit the ticket's citation pins, reports the commit it pinned, and when the working copy differs it reports the difference and asks which source is authoritative before implementing. Acceptance criteria, output messages byte for byte, exit codes and the spec's own fixture identifiers stay literal; exclusions and established ADRs are respected; a genuine issue/spec conflict is reported rather than settled by changing a requirement. Where the tracker is not configured the skill names `/skill:setup-matt-pocock-skills` and does not attempt that user-invoked skill.

Readiness and Git state are checked before any edit. The skill reads the native blocking gate as open blockers only (`issue_dependencies_summary.blocked_by`, with the tracker doc's fallbacks where the capability is marked unverified) and refuses to start a ticket with unresolved blockers unless the human resolves the situation. It inspects the branch, the working tree and the existing commits, reports any partial implementation already present, and asks the human to confirm the branch or worktree the work lands on before editing. It creates no branch, switches none, amends nothing, force-pushes nothing, and runs no destructive Git operation. One implementation task per fresh session, in the foreground, at most one model request live.

The review order is corrected. Upstream runs `code-review` before committing, so `git diff <fixed-point>...HEAD` has nothing to review unless an interim commit already exists; that defect is reported upstream and unfixed there. This fork records the fixed point on the confirmed branch before work begins, commits the implementation, resolves the committed HEAD SHA, checks that the base-to-HEAD range is non-empty and names the ticket's work, and only then loads `code-review` in the session and hands it that pinned fixed point. The two axes stay separate and diagnostic: findings are reported, not applied, and a correction the human approves is committed separately and reviewed as a delta from the previous reviewed HEAD SHA, never as a loop until the report comes back clean. Both dependencies are checked at the point of use: `tdd` and `code-review` are model-invoked, so their names are looked for in the `<available_skills>` block and their `SKILL.md` files read in this session, and a missing one is reported as a missing dependency rather than improvised with generic testing or review advice. `tdd`'s seam-confirmation gate binds from inside `implement`: a seam recorded as human-approved in the spec or ticket is reused without re-asking, and a seam merely inferred or proposed still needs the human's answer, with a one-line note on what it catches and what it misses, before any test is written. The loop stays red to green with no invented refactoring phase, and where the ticket is glue or straight delegation with no independent source of truth to assert against the skill asks the human whether the loop applies at all rather than writing a test that restates the implementation. The run ends at a local implementation commit and a review report: it pushes nothing, opens no pull request, closes or comments on no issue, changes no label, ticks no acceptance box, and starts no next ticket.
