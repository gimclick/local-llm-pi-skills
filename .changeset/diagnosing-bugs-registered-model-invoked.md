`diagnosing-bugs` is now registered in this fork's `pi.skills` manifest, as the seventeenth skill. It stays model-invoked, unchanged in its metadata: its frontmatter carries no `disable-model-invocation` and its `agents/openai.yaml` carries no `policy` block, which is the pairing this fork's registration check reads as model-invoked, so Pi advertises it by name, description and path in the agent's `<available_skills>` block, loads it by reading its `SKILL.md`, and the human can force it with `/skill:diagnosing-bugs` while upstream harnesses type `/diagnosing-bugs`. Its 156-character description and its trigger phrasing are upstream's unchanged; over-triggering on a model with a lower activation threshold is a reported upstream problem (#578) and this fork does not change the description before that behaviour has been observed here. The Pi distribution moves from sixteen registered (eight user-invoked, eight model-invoked) to seventeen, eight user-invoked and nine model-invoked. The Claude plugin manifest is untouched: the promoted set stays 27.

The six-phase methodology survives whole and its gates are unchanged. Phase 1 is still the skill: a **tight, red-capable** loop, one named command already run at least once, that drives the actual bug path and asserts the user's exact symptom, is deterministic, is fast, and is agent-runnable, and no Phase 2 exists without it. All ten loop recipes keep their order and their wording: failing test at any seam, curl or HTTP against a dev server, CLI plus fixture diffed against a snapshot, headless browser script, replayed capture, throwaway harness, property or fuzz loop, bisection harness, differential loop, HITL script last. The tighten-the-loop levers, the non-deterministic goal of a higher reproduction rate rather than a clean repro, the stop-and-ask path when no loop is possible, the Phase 2 minimise rule (done when every remaining element is load-bearing), the Phase 3 requirement of three to five ranked falsifiable hypotheses each stating its prediction and shown before any is tested, the Phase 4 one-variable-at-a-time rule and the `[DEBUG-...]` tag that makes cleanup one grep, the Phase 5 correct-seam criterion and the "no correct seam is itself the finding" exception and the forced-mutation `diff` against a pristine copy before a manufactured red is trusted, the performance branch that measures before it fixes, and the Phase 6 cleanup checklist are upstream's. The `## Redact` section is upstream's and untouched. The Phase 1 gate is not weakened anywhere.

What is adapted is execution. Pi's agent shell is non-interactive, so the HITL last resort cannot run through it: the template reads stdin with `read -r -p` under `set -euo pipefail`, and through the agent's shell that is an EOF, an aborted script, and nothing captured. The skill now resolves `scripts/hitl-loop.template.sh` against the directory holding its own `SKILL.md` rather than the current working directory, because the project under debug is usually not this repository, and hands the human the command to run in their own terminal, taking the captured `KEY=VALUE` block back through the conversation, or a one-question-at-a-time chat capture where one round trip is enough. It states that a captured value is evidence the human supplied, never an invented or predicted one. The script file itself is unchanged, including its recorded mode.

One inference slot governs model sessions, and the skill says so beside the fact that test and process concurrency is ordinary shell work and stays permitted: stress loops, flaky-trigger loops, differential pairs, and parallel test runners are how the reproduction-rate rule gets its rate, and nothing here forbids them. Expensive loops get an iteration or time bound chosen for the task rather than a universal number, a timeout so a hang cannot stall the session, a seed that is reported when randomness is involved, and the observed reproduction rate and measurement conditions stated rather than assumed, so a flake measured at 40 reds in 100 runs is a 40% rate and a fix verified against it is verified at that rate, not as a certainty. Nothing the human owns is interfered with: no server, process, port, or terminal they started is killed, restarted, or taken over.

What this fork adds is authorization, not a workflow. Investigating a bug is authorized; editing persistent project files is not. Being asked to diagnose authorizes reading, running loops, and building bounded experiments in scratch space (a temp directory, a throwaway harness, a replayed capture, a copied module), and it does not authorize editing tracked source, a test file, or project configuration. Before the first such edit, including Phase 4 instrumentation that lands inside project code, the skill states the write set once, names which Phase 3 prediction or Phase 5 fix each change serves, and waits for the human's answer; one approval covers that set and is not re-asked per edit inside it, and where no answer has arrived the run stops at the diagnosis and hands over the findings plus the intended write set. `git bisect` is named as a state-changing operation that needs explicit human authorization, with `git status --short` and the current branch reported, the Git state that will change named, and the `git bisect reset` cleanup given before it is asked for, and a manual "boot at state X, check, repeat" harness preferred over moving the tree. No force-push, no amend, no branch created or switched, and no destructive Git operation without the human's approval. Completion may propose a commit message; the commit, the push, and the pull request stay separately authorized.
