`writing-for-agents` is now registered in this fork's `pi.skills` manifest, as the fourteenth skill. This is a registration, not an adaptation: the skill's `SKILL.md`, its `SKILL-MECHANICS.md`, and its `agents/openai.yaml` are upstream's, unchanged down to the byte, and nothing was added to them for Pi. It stays model-invoked, which is upstream's choice and needs no change here: its frontmatter carries no `disable-model-invocation` and its `agents/openai.yaml` carries no `policy` block, so Pi advertises it by name, description and path in the agent's `<available_skills>` block, loads it by reading its `SKILL.md` (Pi has no Skill tool), and the human can force it with `/skill:writing-for-agents`. Its 103-character description, the conditional pointer to `SKILL-MECHANICS.md` for the skill-specific branch, and all upstream attribution are preserved as they were.

What the registration buys is reachability, not behaviour. The reference is the one every other skill in this set was written against, and it covers the documents the skills produce (a `GLOSSARY.md` and its ADRs, a spec, a ticket), so on a local model it was previously present in the tree but invisible to the agent. Registering it makes the methodology available without restating any of it, and no Pi-specific rule was introduced into the reference just to match the shape of the earlier adaptations.

`README.md` records fourteen registered skills (six user-invoked, eight model-invoked), adds `writing-for-agents` to the Pi status and invocation table as **Validated** under a stated scope, and describes both the registration and the pass that earned the claim; the maturity counts move to thirteen **Validated** and one **Implemented**. `AGENTS.md` moves its Pi registration count from 13 to 14. The docs page gains the fork's Pi banner and keeps its upstream body. The Claude promoted set stays 27: `.claude-plugin/plugin.json` is untouched, and the two registration lists remain independent.

No skill file, no other skill, and no runtime behaviour changed, and nothing new is delegated or executed: the registration adds no dependency, no script, and no subagent.

The maturity claim is **Validated** under a stated scope, from one read-only pass run after the registration landed. The reference was loaded by path and applied to a real adapted skill (`skills/engineering/triage/SKILL.md`), and `SKILL-MECHANICS.md` was loaded through the conditional pointer inside `SKILL.md` because the review subject was a skill; that conditional read is what established that a one-line description carrying no trigger branches is the correct shape for a user-invoked skill, and that triage's hint-not-fire treatment of `/skill:setup-matt-pocock-skills` is the router rule applied correctly. The pass named failure modes in the reference's own vocabulary and cited each to disk: a **cache** where three `gh` spellings in `triage` are byte-identical to the tracker doc that skill is told to read first, **sediment** where the missing-configuration stop is stated twice with different bounds, a step with no **completion criterion** whose write-set successor sits visible below it, restated outcome menus, and a synonym inside a prohibition. Structural observations were kept apart from behavioural ones: every consequence was labelled speculative, because no triage run has been exercised here.

What the scope does not cover: automatic model-invoked discovery, since the pass read the `SKILL.md` by path rather than reaching for the reference from its description; any triage run; and any edit. The findings are unapplied recommendations, and `triage` stays **Implemented**. The Retro integration that must load this reference before that skill evaluates agent instructions is a separate adaptation, deferred until after this registration lands.
