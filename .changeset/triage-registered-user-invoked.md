`triage` is now registered in this fork's `pi.skills` manifest, as the thirteenth skill. It stays user-invoked, unchanged in its metadata: its frontmatter already carried `disable-model-invocation: true` and its `agents/openai.yaml` already carried `policy.allow_implicit_invocation: false`, so it is absent from the agent's `<available_skills>` block and only the human can fire it, by typing `/skill:triage` and describing the work in natural language. The Pi distribution moves from five user-invoked and seven model-invoked to six and seven. The Claude plugin manifest is untouched: the promoted set stays 27.

The upstream lifecycle is preserved and the state machine survives whole. Two category roles (`bug`, `enhancement`) and five state roles (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`), exactly one of each per item, conflicting state roles flagged and asked about before anything else, and the same transitions: unlabeled to `needs-triage`, then to `needs-info`, `ready-for-agent`, `ready-for-human` or `wontfix`, with `needs-info` returning to `needs-triage` once the reporter replies and the maintainer free to override. The five steps keep their order: gather the full issue or PR with its body, comments, labels, author and dates, parse prior triage notes, explore through the glossary and ADRs, and run the redundancy search by domain concept and the `.out-of-scope/` prior-rejection check; recommend a category and a state with reasoning and a codebase summary, then wait for direction; verify the claim by reproducing a bug from the reporter's steps or checking out and running a PR, reporting confirmed, failed, or insufficient detail as the strongest `needs-info` signal; grill when the request needs fleshing out; apply only the approved outcome. The `wontfix` three cases stay upstream's, including the rule that an already-implemented close points to where the feature lives and never writes to `.out-of-scope/`, while a rejected enhancement does. The quick override, the needs-info template, resumability without re-asking resolved questions, the discovery buckets, the external-PR filter as discovery-only, and the mandatory `> *This was generated by AI during triage.*` disclosure are unchanged. No state, role, or label was added, and no scheduler was introduced: `implement-spec` stays out of the manifest.

What this fork adds is configuration authority and two guards, not a workflow. A **Tracker and label configuration** section resolves operations through `docs/agents/issue-tracker.md` and role mappings through `docs/agents/triage-labels.md`, passes the target repository explicitly with `-R` rather than re-inferring it from the remotes, and stops by naming `/skill:setup-matt-pocock-skills` when either file is missing or unconfigured. That skill is user-invoked, so it is named and never attempted. Before any label write the skill reads the mapped label string rather than the canonical role name, reads the labels that exist, and treats a missing one as a fact to report rather than a label to create, rename, or substitute, so an unmapped role cannot silently produce a different write. This is the same rule `to-tickets` already carries, and it closes the upstream bug where the agent applied a role `gh` had never created.

The second guard is a **Readiness guard for `ready-for-agent`**, kept deliberately apart from upstream's classification so the classification stays upstream's. Before recommending or applying that role it reads the issue's open blocking relationships using only the read capability the tracker doc documents: on GitHub the open-only gate `issue_dependencies_summary.blocked_by`, where `blockedBy.totalCount` counts every edge including closed blockers and is never the live gate, with the doc's fallbacks where the capability is marked **unverified** and a statement of which gate was read. The guard then branches on what the gate returned. A verified open blocker means the role is **not applied at all**, and no approval lifts that, because the role means an agent can take the issue now and an issue with an open blocker does not mean that: approval may authorize continuing the investigation, running the grilling step, posting a brief as a comment without the role, or resolving a blocker as a separate operation with its own explicit approval, which is not a label write and is never bundled with the role. After such an operation the gate is re-read, and the role becomes possible only once it returns zero. A verified zero is what permits the role, subject to the write-set approval below. Where the capability is unavailable, unverified, or the gate could not be read, readiness is reported as **unverified**, the unread gate is named, and the role is not applied automatically; the maintainer may apply it as an explicit instruction with that caveat stated. Absence of evidence is not an unblocked issue. The guard removes no blocker, adds or reorders no edge, closes no dependency as part of a role write, and invents no state for work that is specified but waiting, so whatever role the issue already carries stays in place while its blockers are open. Closed edges stay in place, since they record what was resolved. This addresses the most-filed gap upstream without shipping a fix for it: the blocked case is real, its name is undecided, and this fork chose neither.

The intended write set is now explicit rather than implied. Step 5 states the labels to add and the label to remove, the comment to post and whether it closes the issue, and any file to write under `.out-of-scope/`, and applies nothing until the maintainer approves. A **Scope and boundaries** section states that triage is the on-ramp for work arriving from outside and not a step in the spec flow, so tickets that `to-tickets` published are not triaged a second time, and fixes the write surface to labels, comments, closure and `.out-of-scope/` files: no issue creation, no issue-body edit, no sub-issue or blocking-edge change, and no assignment, so triage cannot advance a dependency chain and closing a blocker stays the human's, the same boundary `implement` already holds.

The cross-skill invocation is converted to Pi's pattern. Upstream's step 4 calls the Skill tool twice for `grilling` and `domain-modeling`; Pi has no Skill tool, so the skill checks each name in the agent's `<available_skills>` block at the point of use and reads its `SKILL.md` in this checkout to follow it, both being model-invoked and registered here. A name that is not loaded is reported as a missing dependency and the rest of triage continues with what is already gathered, rather than improvising the missing methodology. An **Execution constraints** section states the single-slot rule: no delegation, no parallel or background work, at most one model request live, one issue worked at a time, and a bulk pass treated as a cheap listing rather than evidence, so each issue's comments and prior triage notes are read before recommending and an issue already carrying a resolution note does not get a fresh brief.
