`handoff` is now registered in this fork's `pi.skills` manifest, as the sixteenth skill. It stays user-invoked, unchanged in its metadata: its frontmatter already carried `disable-model-invocation: true` and its `agents/openai.yaml` already carried `policy.allow_implicit_invocation: false`, so it is absent from the agent's `<available_skills>` block and only the human can fire it, by typing `/skill:handoff` and naming what the next session will be used for after it. Its `agents/openai.yaml` is otherwise unchanged, and no skill and no agent can start a handoff on the human's behalf. The Pi distribution moves from fifteen registered (seven user-invoked, eight model-invoked) to sixteen, eight user-invoked and eight model-invoked. The Claude plugin manifest is untouched: the promoted set stays 27.

The upstream methodology survives whole and its purpose is unchanged: `handoff` buys **portability**, not compression, and it is a document in transit rather than an artifact maintained. All five upstream instructions keep their meaning. The document is still one markdown file written to the OS temporary directory (`$TMPDIR`, else `/tmp`; `%TEMP%` on Windows) and explicitly not the current workspace. It still summarises the current conversation so a fresh agent can continue the work. It still refuses to duplicate content already captured in other artifacts (specs, plans, ADRs, issues, commits, diffs) and still references them by path or URL. It still redacts sensitive information such as API keys, passwords, and personally identifiable information before writing. It still treats a passed argument as a description of what the next session will focus on and tailors the document accordingly. The frontmatter, the `argument-hint` field, and the 86-character description are upstream's unchanged; Pi ignores `argument-hint` silently, since its skill loader reads only `name`, `description`, and `disable-model-invocation`, and the argument itself still arrives because Pi appends text after `/skill:name` as a user request.

What this fork adds is one harness-aware branch inside the suggested-skills section, plus upstream's own size criterion stated where the skill runs. Upstream's Skill-tool instruction stays valid for Claude, so a Claude session reads the same behaviour it did upstream. For Pi, which has no Skill tool, the section names only skills the receiving harness actually has, because a name it cannot find is a dead pointer, and writes the instruction the receiver can act on: a model-invoked skill is named together with its `SKILL.md` to read, whose path the next agent finds in its own `<available_skills>` block, and a user-invoked skill is written as a command for the human to type (`/skill:<name>`), never as something the next agent invokes. That split is `.agents/invocation.md`'s rule, which forbids any skill reaching a user-invoked one, restated for the document a Pi session hands over rather than invented here. The size rule (keep the document a small fraction of the conversation) sits beside the non-duplication instruction, because upstream carries that criterion only in its docs page and a local model with no bound on the summary can restate the session rather than point at it.

What is deliberately not added: no document template, no fixed length, no session-log reading, no durable project-memory location, and no automatic invocation. Pi already keeps each session as a resumable JSONL record under `~/.pi/agent/sessions/` and already compacts long contexts, so the file's unique value in Pi is reach: a document a different harness, a different directory, or a colleague can read. Temp placement stays, because a handoff is not standing project context and a fact that will still be true next month belongs in `CLAUDE.md` or `AGENTS.md` instead.
